# Agibot G2 × Isaac GR00T N1.7 技术报告

更新日期：2026-09-24。本文汇总本仓库已经实施的右臂数据处理、模型后训练、离线评估和 G2 真机推理，可作为项目复盘、简历和技术面试的事实底稿。它记录**实际做过的实验及其证据边界**，不是未经验证的机器人通用成功率声明。操作命令和现行配置以 [操作手册](../README.md)及各任务文档为准。

## 1. 项目范围与主要结论

项目基于 [NVIDIA Isaac-GR00T 的固定上游版本](../../README.md#nvidia-上游)和 GR00T-N1.7-3B 基座，使用 Agibot G2 数采格式建立“原始 episode → 任务筛查 → LeRobot/GR00T 数据 → 单卡 A100 后训练 → 离线评估 → GDK 联合控制真机推理”的流程。已验证的输入是头部和右腕两路 RGB、右臂末端状态及右夹爪；左臂和双臂尚未据此验证。

目前有四条互不混用的任务线。早期抓取在 `10.20.15.60` 上有两次完整抓取记录；`10.20.15.194` 上的 xichong 放置有两次完整放置/释放/回撤记录，zhewan 放置在一次现场失败并修复桥接后有一次现场确认成功记录；最新 xichong 抓取在不同起点测试中出现过“抓起但未入槽”、够不到，以及一轮现场确认“抓起且入槽”。这些都是**有限次数的现场结果**，不构成统计成功率或跨场景泛化证明。

关键工程结论：数据层必须保持动作、视频帧与训练处理器的数学语义一致；训练层必须核对 checkpoint 实际保存的归一化配置；执行层应由同一个 GDK 控制所有者同步下发末端和夹爪目标，按完整 H16 动作块闭环运行。程序检测到“闭爪+抬升”只说明执行反馈满足规则，不能代替人或视觉确认工件是否真正抓住、入槽或放准。

## 3. 系统架构与运行协议

```text
Agibot 原始完整 episode
  ├─ 任务合同/轨迹/图像/时间戳筛查 → 固定 train、heldout 名单
  └─ 下一步 delta 重建 → 10 Hz、两路视频 + Parquet + 元数据/统计量
       → GR00T 官方 loader/processor 审核 → A100 后训练/30k 推理包
       → 推理工作站官方 policy server
       → 实时头部/右腕观测 + G2 状态 → H16 动作块
       → GDK 同一所有者联合执行右 EEF 与夹爪 → 回执/现场结果
```

工作站使用仓库 `pyproject.toml`、`uv.lock` 配置 Python 3.12 环境；机器人保留其厂商 GDK 环境和 Python 3.10，不将工作站环境直接覆盖到 G2。云端单卡 A100 80 GB 承担训练，本机或推理工作站加载包含 `model/` 与配套 `backbone/` 的推理包。更新上游代码时需检查[本地补丁](UPSTREAM_PATCHES.md)。跨机器的相机、GDK 版本、坐标系和夹爪命令均须按[G2 适配检查](G2_ADAPTATION_GUIDE.md)复核。

GR00T 每次给出 **16 条未来动作**；10 Hz 数据下对应 1.6 秒示范时长。“完整推理”是在每块执行并取得反馈后获取新观测，再请求下一块，直到本任务结束条件；不是模型一次产生整条 episode，也不是人为写定抓取/放置轨迹。桥接将每条 10 Hz 末端/夹爪目标交给 50 Hz GDK 控制线程，以 5 个联合 tick 执行。这里没有使用 π0.6 RTC；zhewan 的 H16 原子提交解决逐行网络 ACK 干扰，但同步策略在块间仍需要观测和推理时间。

## 4. 原始数据、清洗与训练表示

### 4.1 原始合同与数据划分

原始数据按 `episode_NNNNNN/` 保存 `frames.jsonl`、`arrays.npz`、采集元数据、质量报告和图像。每帧要核对连续索引、单调时间、任务提示词、`base_link_tf` 位姿、相机索引、当前/下一状态及动作重建；训练相机是 `head_color` 与 `hand_right`，RGB 640×480。原始左腕图像可留在源 episode，但当前右臂模型不把它作为输入。完整字段见[数据协议](DATA_FORMAT.md)。

清洗**按任务语义**而非套用旧任务阈值：抓取检查张开起始、接近、闭合、抬升和末段保持；放置检查初始夹持、释放、回撤。数值/解码通过不等于每条轨迹均由人工逐帧确认物理成功。名单冻结后仅传完整 episode；保留源文件，不在清洗时改变动作、重采样或把连续夹爪强制二值化。留出集不参与归一化统计拟合。

后两任务在转换时对源 JPEG 与解码视频逐帧核对；MP4 使用 H.264 CRF18，是**有损**训练存储，不能声称“图像完全无损”或“压缩对模型效果零影响”。原始 JPEG 未被覆盖。最新抓取数据有一条采集时序警告：一处保存间隔约 0.289 秒，而视频仍在 10 Hz 网格；保留并标记，不用插值掩盖。该任务还保留少量 heldout 数值落出训练 min/max 的诊断。

体积差异主要来自“只保留训练使用的头部/右腕两路、结构化低维字段与 H.264 视频”，而不是静默丢掉大量训练帧：早期抓取原始数据约 29 GB、转换后约 2 GB；最新抓取入选完整源 episode 约 21.90 GB、转换后约 2.426 GB。原始数据包含训练未使用的左腕图像、采集参数、冗余记录和 JPEG 文件组织开销。检查是否缺数据应看固定名单、Parquet 行、两路视频帧和源映射逐项一致，而不能仅看目录大小。[早期体积核对](../examples/xichong_right_single_grasp/RUNBOOK.md)、[最新抓取转换审计](../tasks/g2_194/xichong_right_grasp_r0002/DATA_PREPARATION.md)。

### 4.2 EEF、Rot6D 与夹爪的数学语义

源数据的右 EEF 状态为基座系 XYZ + 四元数 XYZW。源动作是世界/基座系的 `next_delta`：

```text
p_target = p_current + delta_xyz_world
R_target = Exp(delta_rotvec_world) @ R_current
g_target = next_right_gripper            # 下一步绝对值
```

转换器先重建下一步**绝对** EEF 位姿，再把旋转矩阵前两行展平为 Rot6D，连同 XYZ 和夹爪写入 Parquet。模型训练所需的相对 EEF action 由官方 processor 根据当前 state 生成；若把源 delta 直接当成相对模型输入，会造成二次差分。运行时官方解码再将模型的相对 EEF 结果转回基座系目标，由 GDK 使用 XYZ + XYZW。Rot6D 是模型用的连续旋转表示，不意味着传感器或机器人接口使用六维旋转。细节及核对公式见[数据协议](DATA_FORMAT.md)。

这里还有一个容易在面试中说错的坐标关系：官方 `EndEffectorActionChunk.relative_chunking` 以当前窗口的参考 EEF 为原点，对每个未来绝对目标计算 `T_rel,i = T_ref⁻¹ · T_abs,i`；解码时按 `T_abs,i = T_ref · T_rel,i` 复原。它是同一窗口参考下的 SE(3) 相对变换，**不是**把 16 个未来点都做相邻差分，也不是将源数据的 `delta_xyz_world` 不经处理直接当模型 action。夹爪通道没有这层 SE(3) 运算。[官方实现](../../gr00t/data/state_action/action_chunking.py)。

右夹爪保留 GDK native 弧度连续量：约 `−0.785` 为张开，`0` 为闭合；它不是距离米数、不是 0/1 类别。训练和执行均要保持“EEF 相对、夹爪绝对”的区别。每个新机器人/GDK 仍须实测读回开闭端点与方向，不能仅凭字段名沿用旧机参数。

### 4.3 归一化修正

zhewan 数据暴露了旧 q01/q99 percentile 的局限：部分合法回撤状态会被裁剪，训练 state XYZ 最大变化约 65.0 mm，超过 1 cm 的训练帧有 456 条。因此该任务改为仅由训练集拟合 min/max，`use_percentiles=false`；训练集相应大幅裁剪归零（只剩浮点舍入），heldout 仍保留真实超界诊断。首次 100-step 短测虽然能运行，但 checkpoint 处理器仍保存 percentile，因而被判定**不合格**；修复 processor 参数覆盖后重做短测并核实实际 checkpoint 的 min/max，再启动正式训练。此修复不追溯改写旧模型。最新抓取 r0002 同样显式使用本任务训练集 min/max。详情见[zhewan 数据记录](../tasks/zhewan_right_place_r0003/DATA_PREPARATION.md)与[训练记录](../tasks/zhewan_right_place_r0003/CLOUD_TRAINING.md)。

## 5. 单卡 A100 后训练

各任务从适用的 GR00T-N1.7-3B 基座开始后训练；最新抓取 r0002 **不是**从放置任务 checkpoint 续训。云端先核对数据/配置、跑实际 GPU 前向反向及 100-step smoke，再启动 30,000 个 optimizer step。后三条任务的共同配置为单卡 A100 80 GB、per-device batch 16、梯度累积 2（有效 batch 32）、10 Hz/H16、每 5,000 step 保存 checkpoint 且只保留最新两份、每 10 step 记录 loss；正式运行从基座而非 smoke checkpoint 开始。最新抓取采用 AdamW、初始学习率 `1e-4`、cosine、5%/1,500-step warmup、weight decay `1e-5`，实际配置见[该任务训练记录](../tasks/g2_194/xichong_right_grasp_r0002/CLOUD_TRAINING.md)。不能把某任务的归一化设置、数据集路径或 task prompt 直接复制给另一任务。

## 6. 离线评估与“通过”的含义

转换门禁验证结构、帧序、数值重建、视频对应、训练统计量和官方 loader/processor；smoke 验证实际 GPU 能训练及存取模型；离线评估验证模型在示范观测上的开放环输出。这三者都**不**等同闭环机器人成功率。

以最新 xichong 抓取 r0002 为例：8 条训练样本及全部 91 条 heldout（7,358 帧）完成本机 H16 开放环评估，未出现解码失败或原始夹爪越界。heldout 每块首行动作 XYZ 相对示范误差均值 4.53 mm，但全部有效 H16 行均值达 30.15 mm、最大 255.23 mm；首次进入夹持阈值的时机与示范平均相差 0.258 秒、最大 1.4 秒。部分示范观测重置边界出现跨阈值重新张开，未在同一 H16 内观察到该反转。因输入后续仍是示范记录而非模型执行后的真实画面，开放环误差不能直接解释为闭环轨迹偏差或成功率。[完整评估和警告](../tasks/g2_194/xichong_right_grasp_r0002/OFFLINE_TEST.md)。

| 开放环 heldout 指标 | zhewan 放置（58 条） | xichong 抓取 r0002（91 条） |
|---|---:|---:|
| 每块首行 XYZ 相对示范均值 | 7.77 mm | 4.53 mm |
| H16 全部有效行 XYZ 相对示范均值 | 54.69 mm | 30.15 mm |
| H16 全部有效行 XYZ P95 | 196.41 mm | 140.45 mm |
| 开爪/进入夹持阈值时机绝对差均值 | 0.312 s | 0.258 s |

两任务的动作语义、episode 长度和事件定义不同，这张表用于展示**各自长窗口误差明显大于首行误差**，不是对模型优劣的跨任务排行榜。zhewan 在本机 RTX 4090 上实际加载完整模型，338 次 H16 开放环请求的暖态 loopback 平均 0.381 s/块、P95 0.533 s；该计时不含机器人采集、网络与执行。[zhewan 离线报告](../tasks/zhewan_right_place_r0003/OFFLINE_TEST.md)。

zhewan 的离线检查也曾暴露预测时序及长窗口误差，而后续现场表现又证明程序 `PASS` 可与物理失败并存。因此本项目将**数据检查、训练完成、离线诊断、真机执行回执、现场物理结果**分层记录，失败不被软件标志覆盖。

## 7. G2 真机桥接演进

早期方案把机械臂和夹爪交给不同进程/端点交接，出现动作间隙、夹爪开闭与 EEF 不同步等问题。`10.20.15.194` 上验证后的基线改用一个常驻 GDK `Robot` 与单一控制所有者，在同一次官方 `Robot.trajectory_tracking_control` 请求中携带右 EEF `ABS_POSE` 和夹爪 `ABS_JOINT`，统一按 50 Hz 插值发送。推理/通信空档仍由同一所有者保持目标，不通过切换工具进程或自动松爪衔接。详见[连续控制复盘](G2_CONTINUOUS_CONTROL.md)与[运行链路](G2_RUNTIME_FLOW.md)。

**xichong 放置 r0002。** 固定版本 `continuous_20260909` 在 194 机器人连续完成两次完整模型驱动运行，每次 3×H16＝48 行，全部有联合执行回执；实际开爪反馈和回撤分别约 234.9/269.9 mm。操作者确认第一轮完成、第二轮平滑。这里的物理放置精准度没有通过连续多次盲测统计，也不能推断其他 G2 的 GDK 可直接复用。[证据](../examples/xichong_right_place_r0002/STATUS.md)。

**zhewan 放置 r0003。** 首轮虽执行 5×H16、收到开爪与回撤，却被现场判为失败：机械臂停走抖动并危险下压。复盘确认模型目标本身含向下运动，块间等待也客观存在，不能把危险下压完全归咎于网络或夹爪方向。[失败记录](../tasks/zhewan_right_place_r0003/LIVE_TEST_20260911.md)。后续版本 `h16_collision_latched_20260911` 将完整 H16 原子提交、冻结启动校准后的补偿、开启并读回 GDK 碰撞配置，同时增加碰撞/模式异常后的软件锁存：阻止继续发布余下目标，不自动清错、张爪或复位。一次复测完成 4×H16＝64 行，实际释放并回撤约 231.45 mm，操作者确认现场动作可接受。[部署与复测](../tasks/zhewan_right_place_r0003/BRIDGE_DEPLOYMENT_20260911.md)。软件锁存不是硬件急停；这轮无碰撞触发，不能宣称已实测碰撞拦截效果或彻底消除所有抖动。

## 10. 数据流水线的工程实现

### 10.1 为什么按完整 episode 筛选，而不是只传图片

一条训练轨迹不仅包含 RGB 图像，还包含逐帧当前末端/夹爪状态、下一步动作、时间戳、任务语言、采集配置和质量报告。只拷贝筛选出的 JPEG 无法恢复源动作的 `next_delta` 语义、帧序与相机—状态同步关系。最新抓取 r0002 因此先在机器人端盘点全部 851 条（76,560 帧，约 39.08 GB），完成数值审计和 153,120 张训练相机 JPEG 的全量解码；再按固定名单传输 **491 条完整 episode**。其原始文件约 21.90 GB，经约 512 MiB 一包的 tar+zstd level 1 无损分包，43 包传到本机，支持按包续传。传输核对的对象是文件路径、大小、每条 episode 文件数和总字节数；源数据和未入选 episode 未被删除。详细工具链是 [`inventory_raw.py`](../tasks/g2_194/xichong_right_grasp_r0002/inventory_raw.py)、[`screen_numeric.py`](../tasks/g2_194/xichong_right_grasp_r0002/screen_numeric.py)、[`compare_subsets.py`](../tasks/g2_194/xichong_right_grasp_r0002/compare_subsets.py)、[`pack_selected.py`](../tasks/g2_194/xichong_right_grasp_r0002/pack_selected.py)及[`pull_packed.py`](../tasks/g2_194/xichong_right_grasp_r0002/pull_packed.py)。

数据选择也不是“全部成功标签取前 400 条”：最新抓取训练集覆盖两天的 7 个采集会话（227+173 条），首个完整会话 91 条独立留出；训练和留出 UUID 不交叉。会话隔离防止相邻高度相似 episode 混入两边，但**留出集仍是同工位数据**，不能将它当成全新场景泛化测试。早期抓取则从严格同步候选中做时间分层与归一化轨迹特征 k-center 选择，以减少连续重复轨迹。四任务的选择策略有共同原则，却不是同一组机械运动阈值。[最新抓取名单与结果](../tasks/g2_194/xichong_right_grasp_r0002/README.md)、[早期选择方法](../examples/xichong_right_single_grasp/RUNBOOK.md)。

### 10.2 转换产物与全量一致性门禁

转换输出是 LeRobot 格式的 `data/*.parquet`、`videos/*/*.mp4` 和 `meta/*`，而不是单个训练 CSV。Parquet 保存每帧 state/action；两路视频各对应同一 episode 的 10 Hz 帧序；meta 保存任务语言、modality、训练统计量、原始 episode 映射及采集时间。原始相机采集可能有时间抖动，视频按固定 10 Hz 编码不意味着源时钟无抖动；最新抓取把真实 `timestamp_monotonic` 单独保存在元数据中，并标出 0.289 秒延迟帧。[转换约定](DATA_FORMAT.md)、[最新抓取处理细节](../tasks/g2_194/xichong_right_grasp_r0002/DATA_PREPARATION.md)。

自动门禁分层进行：

1. **原始完整性：** 合同字段、任务/机器人 ID、UUID、帧号、时间递增、数组形状、有限值、四元数、相机路径及解码；核对 JSONL 与 NPZ 中状态/动作的一致性。
2. **数值重建：** 从当前位姿加源 delta 重建下一步绝对目标，并与源记录中的 `next_right_ee_pose` 对照；Rot6D 正交性、源动作与输出 Parquet 的浮点误差分别记录。
3. **视频对应：** 逐帧解码所有训练相机 MP4，与相同索引的源 JPEG 对照，检查数量、顺序及 PSNR；不是只抽第一帧检查画面可播放。
4. **官方处理器：** 用 GR00T 实际 `LeRobotEpisodeLoader`、`StateActionProcessor` 和任务 modality 加载训练/留出数据，核对完整 H16 数学往返、相对 EEF 处理、夹爪绝对值与归一化统计来源。
5. **名单与语义：** `train.txt`/`heldout.txt` 不重叠，任务语义采用该批采集合同。关键帧人工抽查的覆盖范围另记，不能把自动检查 PASS 写成 491 条物理抓取全量审核通过。

最新抓取转换数据由 491 个 Parquet 和 982 段视频组成，训练/留出共 42,466 行；视频解码、全帧图像对应、数值重建与官方处理器验证均完成。状态/动作相对源的最大逐元素差约 `2.98×10⁻⁸`，官方相对 EEF 数学核对最大约 `6.83×10⁻⁸`；这是 float32/计算一致性，**不是机器人毫米级定位精度**。训练/留出最低逐帧 PSNR 为 36.418/36.552 dB，说明编码没有出现该阈值下的明显错帧或严重劣化，却不能推出模型效果完全不受压缩影响。完整结果见[数据处理记录](../tasks/g2_194/xichong_right_grasp_r0002/DATA_PREPARATION.md)。

### 10.3 训练统计量与分布外样本

模型既处理绝对 state，也处理相对 action；每个 modality 的统计量必须来自本任务的训练集，并与保存的 processor 一同进入推理包。zhewan 的 q01/q99 问题不是“计算出的轨迹坐标错了”，而是合法尾部 state 在处理器中被裁剪。改用训练 min/max 后，训练集的最大位置恢复差由约 65.036 mm 变为浮点舍入量级；留出集中仍有少量状态超界，最大约 11.861 mm，因不能用留出数据扩张训练边界而如实保留。最新抓取 heldout 的少量超界也单独报告，最大 XYZ 还原差约 4.05 mm。若面试被问“为什么不用更鲁棒的 percentile”，准确回答是：**这批任务存在低频但合法的回撤状态，裁剪会直接改变示范状态语义；最终选择是训练分布覆盖与裁剪诊断之间的具体取舍，不是 min/max 永远优于 percentile。**

## 11. 模型训练与 checkpoint 的技术细节

### 11.0 GR00T N1.7 在本项目中怎样产生动作

仓库当前 `Gr00tN1d7` 由 Cosmos-Reason2-2B/Qwen3-VL 架构的视觉语言骨干与 action head 组成。骨干提取两路图像及任务语言特征；action head 编码当前机器人 state、待去噪的动作序列和时间步，通过带视觉语言条件的 DiT/AlternateVLDiT 预测动作速度场。本项目**使用并后训练官方架构**，没有自行发明网络层或训练目标。动作头源码见[`gr00t_n1d7.py`](../../gr00t/model/gr00t_n1d7/gr00t_n1d7.py)，模型配置见[`gr00t_n1d7.py`](../../gr00t/configs/model/gr00t_n1d7.py)。

训练时从真实动作 `a` 和高斯噪声 `ε` 构造 `x_t=(1−t)ε+t·a`，监督速度 `v=a−ε`；loss 是动作 mask 覆盖元素上的预测速度与目标速度的均方误差，按有效元素数归一。推理从随机噪声动作序列开始，以默认 4 个去噪/流积分时间步做 Euler 更新，再由 processor 反归一化和恢复绝对 EEF。故 `train/loss` 反映的是该监督目标下的拟合，不是“末端真实误差米数”或机械臂控制损失。模型配置的最大 action horizon 容量可以是 40，但**本任务 modality 的 `delta_indices=0…15`，实际训练/解码有效动作是 H16**；不能把 40 的张量容量说成每次执行 40 步。[本任务 modality](../tasks/g2_194/xichong_right_grasp_r0002/modality.py)。

### 11.1 训练哪些参数、资源如何控制

模型是已有 GR00T N1.7 3B；项目完成的是任务后训练，不是从零预训练一个 VLA。单卡 A100 80 GB 配置主要训练 projector 和 diffusion/action 模块，冻结 LLM 主体与视觉编码器，沿用模型配置的 `tune_vlln=true`；训练以 BF16/TF32 运行，使用 state dropout `0.2`、亮度/对比度/饱和度/hue 颜色增强（最新抓取分别 0.3/0.4/0.5/0.08）、4 个 dataloader workers。最新抓取的梯度裁剪 `max_grad_norm=1.0`；`episode_sampling_rate=0.1` 是加载器的随机采样参数，**不是固定只训练 40 条 episode**。[完整参数表](../tasks/g2_194/xichong_right_grasp_r0002/CLOUD_TRAINING.md)。

有效 batch 为 `16 × 2 = 32` 个样本/optimizer step。30k step 名义上约 96 万次样本曝光；对最新抓取的 35,108 帧而言相当于约 27.3 倍保存帧数，但随机采样和 H16 窗口使它不是严格的 27.3 个顺序 epoch。学习率 `1e-4`、AdamW、cosine、5% warmup 与之前单卡成功配置保持一致，是有依据的**起始配置**而不是完成了网格搜索后的全局最优。30k 是既定预算和可比较的训练节点；验证实际部署还需要 heldout 与真机结果。

### 11.2 为什么训练前必须有 100-step GPU smoke

仅有 `uv sync`、CPU 文件清单和官方模型索引检查，无法保证 CUDA 模型加载、batch 前反向、BF16 数值、显存和 checkpoint 保存能工作。100-step smoke 真实跑训练与保存，并重新加载输出处理器核对统计量。最新抓取 smoke 退出码 0，前/后 10 步平均 loss 1.2374/0.9409，显存抽测约 39.4 GiB，未 OOM；这个数值是采样，不是峰值。zhewan 首次 smoke 恰好揭示 processor 的 `use_percentiles` 覆盖未生效：loss 下降也不能批准错误的预处理配置。修复后重跑并检查保存后的配置，正式 30k **从基座重新开始**，没有续接临时 smoke 权重。

### 11.3 checkpoint、模型包与完整性

每 5k step 保存一次，保留最近两份可降低数据盘高峰占用，通常最终可见 25k/30k。正式 checkpoint 可包含模型、optimizer、scheduler、RNG 与 Trainer 状态，供准确续训；下载到本机的推理包则以 `model/` 加配套 `backbone/` 和 processor 配置为加载单位，不等价于完整续训状态。迁移模型包时需要保持骨干路径正确，不能单拷 3 片权重而丢失模型索引、processor、modality 或骨干。[模型下载与使用说明](../README.md#25-从-hugging-face-下载)。

损失日志按 10 step 记录，能排查 NaN、梯度异常和是否继续下降，但训练 loss 同时受任务轨迹长度、采样、归一化和模型噪声影响。早期抓取、两个放置和新抓取的绝对 loss **不可跨任务直接排名**。若要判断 25k 还是 30k 更适合，至少要在同一 heldout 协议及现场起点条件下对照；仅凭 30k loss 更低不足以宣称实机更好。

## 12. 从 Policy 输出到 GDK 动作的逐层语义

### 12.1 推理输入与处理器

机器人侧只读观测服务提供头部与右腕图像、右 EEF `base_link→arm_r_end_link` 的 XYZ/XYZW、native 夹爪位置和时间戳。工作站适配层保证图像通道/尺寸与训练 modality 一致，将四元数转为训练所用 Rot6D，构造带 batch/time 维度的 state、video 和训练任务文本，然后发送至官方 `gr00t/eval/run_gr00t_server.py`。预热调用只加载/预热模型，动作丢弃；`policy.reset()` 重置策略状态，**不是机器人运动复位**。激活动作 bridge 之后再获取新鲜观测开始正式循环。[运行顺序](G2_RUNTIME_FLOW.md)。

模型内部输出的是归一化动作张量；官方 processor 的 `decode_action`/`unapply_action` 执行反归一化，并针对配置为 `RELATIVE` 的 EEF 使用当前 state 恢复绝对目标。机器人桥接拿到的是物理目标，而不是仍待加到当前 EEF 上的 delta。再加一次当前 XYZ、再除/乘一个“单位比例”或再次归一化夹爪，都会造成系统性偏移。最新抓取任务的独立单元测试、离线评估和逐行实机回执都专门核对这条边界。[处理器实现](../../gr00t/model/gr00t_n1d7/processing_gr00t_n1d7.py)、[状态/动作处理器](../../gr00t/data/state_action/state_action_processor.py)。

### 12.2 GDK 联合请求与物理单位

在当前验证的 194 配置中，应用以官方 GDK `Robot.trajectory_tracking_control` 发送同一时刻的 `right_arm: ABS_POSE` 和 `right_effector: ABS_JOINT`：前者为 base_link 米、XYZW 四元数，后者为 native 弧度值。参考姿态需要按本机 GDK 的 `arm_r_link3` 等语义初始化，不能把右 EEF 四元数直接用作 link3 参考；该步骤仍需在新 GDK 上核实。曾有 raw-native 联合接口的静止持位实验出现毫米级下移，它不是后来经过反馈标定、完整验收的 continuous 版本，不能混为同一个测试结果。[历史 GDK 接口研究](G2_NATIVE_TRAJECTORY.md)、[已验证运行路径](G2_RUNTIME_FLOW.md)。

应用层 50 Hz 插值可概括为 `p(α)=(1−α)p0+αp1`，夹爪也在 5 个 tick 内从前值线性过渡到模型目标。姿态对四元数先作符号对齐（内积为负时翻转一端），再作归一化线性插值 NLERP；它**不是** SLERP，也没有保证加速度或 jerk 连续。每个 10 Hz 模型 waypoint 对应 5 个 20 ms 联合发布 tick，完整 H16 名义动作段有 80 tick。50 Hz 是应用对 GDK 的发布频率，不表示相机或视觉策略以 50 Hz 推理，也不等于厂商内部伺服的全部频率。

### 12.3 反馈、回执和控制权

应区分四个事实：策略生成目标 → 机器人动作服务接受入队 → GDK 发布/执行完成回执 → 实际 EEF/夹爪反馈与现场工件结果。单次 ACK 或 SDK 返回 0 不意味着物理到位；夹爪关节接近 0 rad 不意味着金属件已入槽。一个机器人会话只有一个活动动作 owner，启动时桥接先 standby；模型就绪并完成预热后显式 activate，执行期间同一线程持续发 arm/tool，不同时运行旧 mux、独立工具 daemon 或竞争 controller。完成或异常退出时停止继续发布，不在 `finally` 中自动张爪、闭爪或复位。这样既避免工具交接造成断续，也避免持件时清理动作造成事故。

## 13. 推理连续性、抖动与安全机制的实证分析

### 13.1 旧 arm/tool 交接为什么慢

历史 mux 在夹爪动作时停止机械臂子进程、等待工具端点、重启机械臂并重新标定；一次夹爪行阻塞约 10.38 秒，而实际工具张开约 0.51 秒。故表面“夹爪太慢”并不主要来自机械开闭本身。替换为单 owner 联合轨迹后，模型的中间夹爪开度也能与每行 EEF 目标同步插值发布，无需只在开/闭端点进行进程交接。这是**应用和 GDK 官方接口集成**，没有改厂商底层驱动、IK 或固件。[演进记录](G2_CONTINUOUS_CONTROL.md)。

### 13.2 H16 原子提交优化了哪一段

同步系统单轮可分解为“新观测/状态读取 → 模型 H16 计算 → H16 提交/等待执行 → 下一轮”。旧逐行网络请求使块内 100 ms 目标节奏受跨网 ACK 和状态请求影响。zhewan 失败轮四次块间空档约 1.24、2.18、1.42、1.30 s，块内间隙 P95 约 140 ms；与此同时模型单块计算约 0.31–0.35 s，说明空档不能全部推给神经网络。原子 H16 的应用语义是**16 行先整体校验再入队**，机器人本地线程按 10 Hz/50 Hz 节奏发送，每行独立 ID 和完成回执；无效末行、重复 ID、非活动 owner、未清空的旧队列均拒绝。接收结果不确定时不盲目重发，以免重复物理动作。所谓“原子”不表示物理动作不可中断，也不是断网后的 distributed exactly-once 保证。[实现与测试记录](../tasks/zhewan_right_place_r0003/BRIDGE_DEPLOYMENT_20260911.md)。

zhewan 成功复测 4 个 H16 周期累计 10.325 秒（不含模型预热/校准）；每次提交至完成约 1.662/1.769/1.702/1.765 秒，接近 1.6 秒名义执行时长。该轮模型计算约 0.508/0.441/0.332/0.295 秒。不能将失败轮 80 行耗时与成功轮 64 行耗时直接计算“提升百分比”：动作数量、模型轨迹和计时边界均不同，也没有固定同场景随机性。更准确的表述是“减少了逐行跨网络 ACK 对块内节奏的依赖，并在一轮实机验证中完成 64 行、释放与回撤”。

### 13.3 补偿冻结与碰撞锁存

旧 continuous 控制中应用可能根据 `desired − measured` 的误差持续更新位姿补偿。这个误差既包含静态偏差，也包含运动过程中的动态跟踪滞后；若不断积累为偏置，可能造成追赶和回摆。zhewan 固定版本只在启动校准期间学习并在正式执行中冻结**应用补偿**，不是断开 GDK 内部反馈。这个机制解释合理，但一轮复测同时改变了传输与锁存配置，**没有单变量消融证明冻结补偿独自消除了抖动**。[zhewan 部署](../tasks/zhewan_right_place_r0003/BRIDGE_DEPLOYMENT_20260911.md)。

GDK 原生碰撞检测曾从读回关闭变为开启、灵敏度 3、恢复等待 500 ms；应用在碰撞对、错误、控制模式异常或读取失败时锁存故障并拒绝后续目标。500 ms 是为了更容易观察模式变化，不是容许碰撞持续半秒；软件锁存不能撤销已经发到固件的控制点，也不替代急停。本轮成功运行未触发真实碰撞，因此它验证了配置、软件链路和正常流程，**没有验证真实碰撞时的停止时延**。未启用自定义力/最低 Z guard，因为缺少现场标定的物理阈值；训练全局 XYZ 包络也不等于夹具局部接触安全区域。

### 13.4 最新抓取的“微平滑”到底做了什么

新抓取任务的平滑仅在整个 H16 块都保持张爪、低速、小净位移、首行与当前反馈相近时，处理开爪悬停微调路径；保留块首/末端、16 行长度、所有夹爪目标，并跳过闭爪/抬升块。最新录像两轮最大 XYZ 调整只有约 0.46/0.49 mm；真正决定能否够到的闭爪块未被改动。另一次 6 块实机运行虽配置了平滑，6 块均未触发，不能把该轮看似更顺的动作归功于滤波。该选项也不是 RTC、MPC 或硬编码抓取轨迹。若面试谈“做了推理优化”，应明确它是**受限条件下的路径微调及诊断功能**，不是已经证明提高成功率的核心成果。[触发逻辑与报告](../tasks/g2_194/xichong_right_grasp_r0002/BRIDGE_DEPLOYMENT.md)。

## 14. RTC 实验及为何没有纳入最终流程

曾探索 GR00T 上的异步动作续接/velocity-ramp RTC：机器人执行旧动作时生成新预测，已提交目标保留，未提交目标可融合。为此必须把旧物理动作前缀按**新观测的状态参考**重新编码为相对 EEF 和 checkpoint 统计量；不能直接拿旧归一化张量或 GDK 的 XYZ/XYZW 命令塞给模型。时间线要区分动作“提交”与“机器人完成”，并满足 `0 < F ≤ O < H`（F 为冻结长度，O 为可对齐重叠长度，H=16）。[实验设计](../rtc/README.md)。

194 机器人上的实验性真机运行有 4 次 RTC 合并成功，但后续队列耗尽，现场认为放置失败。已定位的调度缺陷是固定 `F=8`，同时等剩余队列 ≤8 才请求新预测；相机起点前移后 `O` 降到 7，条件 `F≤O` 永不再满足。软件后续修了触发时机和窗口计算，但**修正后的真机效果尚未复测**。这不是“RTC 原理无效”的证明，也不是最终基线采用了 RTC。[失败与修正记录](../rtc/LIVE_TEST_20260909.md)。

实验后一次人工复位决策在未确认工件承接/夹爪释放时先闭爪回撤，用户报告险些损坏工件/夹爪；这是现场操作决策错误，不是模型输出。正式流程因此保留已验证的同步 H16 与单 owner 联合控制。若未来重启 RTC 工作，应建立同初始条件的 A/B，对比块间等待、执行目标与反馈、夹爪转换时机、物理入槽/放置，而非只看录像主观平滑度或单次模型耗时。

### 17.2 值得重点讲的三个工程案例

**案例 A——数据/处理器一致性。** 问题：源数据是 base_link 下下一步 delta，模型需要相对 EEF 表示，且 zhewan 旧 percentile 裁剪了合法回撤。实施：先重建绝对目标、用官方 processor 生成相对 EEF，冻结训练/留出名单，逐帧对齐视频与 Parquet，检查官方处理器实际加载的统计量；发现第一次 smoke 仍保存旧 percentile 后修代码并重做。结果：zhewan 400/58 条、25,436 个 H16 数学窗口验证；30k 训练保存 min/max 配置。要点：**不是“做了简单格式转换”，而是追踪原始语义、训练表示和推理反变换。**

**案例 B——机械臂/夹爪衔接。** 问题：旧 mux 在工具切换时停止/重启机械臂服务，造成秒级空档与中间开度不同步。实施：核对官方 GDK 联合轨迹结构，使用同一个控制 owner、同一请求中 `ABS_POSE+ABS_JOINT`、每模型行 5 个联合 tick，并区分接受回执与实际开爪反馈。结果：xichong 放置两轮各 48 行完整执行，现场确认第二轮流畅。要点：**解决的是控制权、时间线和语义对齐，不是只改夹爪符号。**

**案例 C——现场失败驱动的诊断。** 问题：zhewan 程序报告释放/回撤，但现场抖动并下压；最新抓取软件反馈闭爪/抬升，却有未入槽和够不到。实施：对齐模型目标、桥接下发、GDK 反馈、块间耗时和同步视频；zhewan 改 H16 原子提交/补偿冻结/碰撞锁存，新抓取用只读录像和 AprilTag 场景尺度检查定位分布偏差。结果：zhewan 修订版一轮现场确认成功；新抓取两轮录像中一轮现场确认抓起且入槽。边界：这些是**组合改动与具体试验的结果**，没有因果消融或统计成功率。

### 17.3 高频技术追问的短答

- **为什么 EEF 不直接用四元数训练？** 传感器/GDK 仍用 XYZW；模型 EEF 部分按上游约定用旋转矩阵前两行的 Rot6D，训练和部署在适配层转换。关键是约定一致，不是四元数不能用。
- **10 Hz 和 50 Hz 分别是什么？** 示范和模型目标每 100 ms 一行；GDK 应用每 20 ms 发布一次插值后的联合 arm/tool 目标，5 tick 对应一行。模型不是 50 Hz 推理。
- **H16 为什么不算固定程序？** 每 16 行都由当前图像、状态和任务文本动态产生；执行完成后读取新观测继续。任务完成判据用于决定何时停，不指定固定抓取/放置坐标。
- **为什么不用 RTC？** 做过真机异步续接实验，但调度缺陷导致队列耗尽且放置效果失败，修正版未完成真机复测；最终保留现场验证过的同步 H16。不能宣传 RTC 已部署并改善性能。
- **训练 loss 低为什么还会失败？** loss 衡量训练样本上的预测目标，不覆盖相机—工装几何变化、闭环误差积累、接触和入槽质量。最新抓取失败轮的视觉尺度相对训练中位偏 −6.17%，即使执行反馈正常也会够不到。
- **“碰撞保护”是否保证不会压坏工件？** 没有。GDK 配置和应用锁存阻止进一步发布是分层保护，但真实触发时延未测、已下发点不能取消，且训练包络不是夹具安全空间；现场急停和清场仍必要。
- **如何给出真实提升数字？** 先固定任务、起点、工件、随机种子/预测设置及同一计时边界，收集多轮 baseline/候选的块间 gap、反馈轨迹、完成质量和异常；现有不同长度的失败/成功轮不能直接算百分比。

## 19. 测试层级与复现清单

项目验证不是一个“所有测试 PASS”的笼统标志，而是由相互不能替代的层级组成：

| 层级 | 实际检查 | 不能替代的下一层 |
|---|---|---|
| 静态/配置 | Python 编译、shell 语法、路径与 modality、固定版本来源 | 真实模型/数据加载 |
| 原始与转换数据 | 源 episode 合同、图像解码、动作重建、全量对帧、训练/留出隔离 | GPU 前向反向与模型质量 |
| 官方 loader/processor | H16 相对 EEF/绝对夹爪往返、统计量及裁剪诊断 | 保存 checkpoint 的实际配置与训练稳定性 |
| GPU smoke | 100 step、loss/梯度有限、显存、checkpoint 保存与重载 | 30k 收敛与 heldout 表现 |
| 正式训练 | 30k 退出码、日志、25k/30k checkpoint、推理包重载 | 开放环预测与闭环效果 |
| 离线开放环 | 真实权重对训练/heldout 观测 H16 预测、解码、参考误差与时序 | 真实相机和 GDK 动作执行 |
| 假机器人/TCP 回归 | 控制协议、完整回执、5 tick 插值、owner/队列/故障语义 | 厂商控制、接触和现场任务成功 |
| 只读真机准备 | 相机、TF、夹爪和模式读回、场景画面、动作服务 standby | 实际运动、真实碰撞响应 |
| 现场闭环试验 | 完整 H16、目标/反馈/录像/现场工件结果与异常处理 | 长期统计可靠性和安全认证 |

复现新抓取的数据/训练流程时，主要入口是[任务 `prepare.py`](../tasks/g2_194/xichong_right_grasp_r0002/prepare.py)、[`prepare.json`](../tasks/g2_194/xichong_right_grasp_r0002/prepare.json)、[`modality.py`](../tasks/g2_194/xichong_right_grasp_r0002/modality.py)、[`train_1xa10080.env`](../tasks/g2_194/xichong_right_grasp_r0002/train_1xa10080.env)、[`train.sh`](../tasks/g2_194/xichong_right_grasp_r0002/train.sh)和[单卡 launcher](../training/launch_1xa10080.sh)。zhewan 使用独立的[任务配置](../tasks/zhewan_right_place_r0003/prepare.json)与[训练记录](../tasks/zhewan_right_place_r0003/CLOUD_TRAINING.md)。通用流程、依赖和模型下载见[操作手册](../README.md)，不在技术报告中复制可能过期的远程服务器命令和机器人启动命令。

报告使用的是仓库历史与截至 2026-09-24 的本地记录；各机器人后续可能被人重新定位、断电、换 GDK 或调整工件。任何新的现场运行都需重新核对实时状态，不能把这里的末态坐标或碰撞配置当成当前有效状态。对面试来说，这也是一个重要的工程区别：**可复现的配置与可审计的历史证据，不等于现在这台机器人天然已经准备好运行。**
