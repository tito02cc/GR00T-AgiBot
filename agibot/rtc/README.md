## 算法与范围

在旧动作仍执行时预测下一块，并以旧动作的未执行前缀约束新预测；已提交执行的动作
不回放、不被新预测替换。目标是减少等模型导致的停顿和新旧动作块交界处的不连续。
它不能保证解决同一动作块内部的来回运动、策略在任务完成后反复修正或 GDK 跟踪振荡。

这里接入的是仓库现有的 GR00T **velocity-ramp RTC 原语**：固定前 F 步，随后逐渐
增大重叠段的去噪更新。它不是完整复现 PI 论文的引导算法，也不是 π0.6 的训练时机制。
官方把它标为实验性低层接口；普通 `Gr00tPolicy` 不会仅凭传入 RTC options 自动启用。
参见[官方部署说明](../../getting_started/real_world_deployment.md)、
[GR00T 实现](../../gr00t/model/gr00t_n1d7/gr00t_n1d7.py)、
[PI RTC 介绍](https://www.pi.website/research/real_time_chunking)。

本案例训练有效 horizon 为 **16**，10 Hz；模型张量容量40不是40步有效训练动作。
当前实验仅支持 B=1、右臂 `right_eef` 9D + `right_gripper` 1D；这不代表算法只支持右臂。
官方文档建议更长的动作块；当前 H16 是否有足够延迟余量仍需实测，不为此修改训练配置。

## 动作表示与时间对齐

前缀必须是**与新观测同一时间起点的绝对物理动作**；从采样到收到图像期间已经提交的
部分也要从历史中保留、计入冻结窗口，绝不能重发。不能直接复用上次
归一化后的模型张量，也不能把 G2 的8D命令当作模型10D动作。

- EEF 按新原始状态做官方 SE(3) relative 转换，再用 checkpoint 的统计量归一化。
- 统计量可能带16步时间轴。临时把物理前缀补到有效 H16，用新块的前 O 槽统计编码；
  仅实际前 O 行进入 RTC，其他模型槽仍按官方规则 padding。不能沿用旧块末尾槽统计。
- 夹爪仍是 absolute native radians：本机 `0` 闭合、`-0.785` 张开。
  前缀适配不加平滑或反转；输出继续复用既有解码器及其物理开度范围处理。
- 原观察处理和 checkpoint 不变。单独前缀处理器禁用输入裁剪，但官方 min/max
  反归一化仍会裁剪。因此逐次验证物理往返；无法表示的前缀显式报错，不偷偷改坐标或统计。
  这里检查的是编码误差，不是给机器人运动添加微米级到位条件。
- bf16 conditioning 误差单独记录；返回的冻结 F 步恢复为原物理 float32 值，队列也保留
  旧目标原值。冻结输出相同是实现保证，不能用它证明模型质量或实际减抖效果。

`ActionQueue.pop()` 表示目标已经**提交给执行器**，不是机器人已经到达该点。
真机入口通过机器人同机 wall/monotonic 配对，将传感器时间映射到行执行时间线，
支持最近32个已提交目标的历史起点。行内采样对应该行终点，冻结已提交行；这是10 Hz行级
量化，不是精确伺服采样对齐，也不是证明物理到位。桥接仅新增行开始/结束时间遥测。
不能只比较相机网络响应时间，也不能直接把旧 runner 换端口就宣称完成 RTC。

参数含义：H=16，O=从观测起点到旧计划末尾的动作数（含采样后已提交部分），
F=推理期间保留的前缀长度，满足
`0 < F <= O < H`。若预测期间提交数超过 F，新结果过期，不从头重放或挪到当前时刻。
服务延迟应包括观测、编码、模型、通信和调度；F 应依据该总延迟的实测高分位确定。
脚本默认 O=8/F=4 仅用于静态协议检查，**不是本机实时部署参数**。

## 软件验证

在仓库根目录运行，无机器人连接：

```bash
.venv/bin/python -m unittest discover -s agibot/rtc -p 'test_*.py' -v
```

2026-09-09：59项测试通过。覆盖官方状态/动作处理器、H16逐时间统计、旋转参考系、
bf16误差、有损前缀拒绝、异步消费、不回放已提交动作、冻结段保持、过期结果、
队列耗尽、线程归属和服务回执。软件测试不代替真机效果对比。

先用保存的观测直接加载现有模型：

```bash
.venv/bin/python agibot/scripts/check_gr00t_rtc_saved_observation.py \
  --snapshot-dir /data/task/saved_observation \
  --model-path /data/task/checkpoint-30000/model \
  --prompt '任务训练时使用的指令' \
  --overlap 8 --frozen 4 \
  --report /data/task/reports/rtc_interface.json
```

观测目录含 `metadata.json`、`head_color.jpg/png` 和 `hand_right.jpg/png`，采用已有
`capture_g2_observation.py` 的保存格式。模型/观测/报告路径由使用者填写；报告不覆盖旧文件。
报告 `PASS_INTERFACE_ONLY` 仅表示该观测上的 RTC 调用成功、输出有效16行且冻结字段一致。
它使用同一静态观测下普通预测的**前 O 步**作为合成前缀；不能拿末 O 步搭配未推进的
观测假装异步 rollout，更不能由此判断抓取/放置成功率。

本地实际30k权重检查已通过，记录为
`agibot/local_reports/rtc/20260909_saved_observation_v2.json`（不入 Git）：

- 实际调用官方 RTC 去噪；返回16个 EEF/夹爪动作；冻结物理字段完全一致。
- 本次归一化往返最大位置误差约 `2.50e-16 m`；bf16 conditioning 位置误差约
  `5.92e-8 m`、旋转误差约 `0.000848°`，是单次样本结果。
- 单次 RTC 调用约 `0.474 s`，包含本地前后处理；普通首调用约 `1.445 s`。
  冷热状态不同，不能据此声称 RTC 加速3倍。`0.474 s` 已超过4个10 Hz动作的时间，
  进一步说明测试用 F=4 不能直接用于这台机器的异步执行。

初次检查发现并修复了 O长度前缀与16槽统计不匹配的问题；失败报告 v1 保留用于追溯。

```bash

  --model-path /data/task/checkpoint-30000/model --port 5565
```

异步接入已尝试，但没有完成任务，不能据此宣称减抖成功。

信号做平均，也不把多种算法一次叠加导致无法判断效果。
